# 06 离线模式与状态上报

> 结论先行：**没有"离线游玩"**（登录/存档/经济都在服务端），但**有"断线容错 + 离线收益 + 埋点补传"**三套机制。
> 因此"离线时能不能刷、上线后怎么补报"的答案不是一个是/否，而是要看**离线收益的时间差由谁计算**。
> 这一篇给出证据链、三种可能的机制、以及一个能在真机上 30 分钟出结论的判定实验。

## 1. 四种"离线"必须分开谈

| 语义 | 本作是否存在 | 证据 |
| --- | --- | --- |
| A. 真离线游玩（断网可进可玩） | **不存在** | 登录态、实名/防沉迷、存档、经济全在服务端；`ParkConfig.json` 指向 `park_server_region: lilith` 生产环境 |
| B. 断线容错（短暂断网 → 本地继续表现 → 重连补状态） | **存在** | `libil2cpp.so` 含 `UnityWebSocket.Runtime.dll`、`KCP`、`reconnect`、`session`；`libigame.so` 含 `KCP` |
| C. 离线收益（放置/挂机） | **存在（模块在包里）** | 未加密索引还原出 `EIdle`、`FIdleK`、`KIdlev`；同步/上报模块 `Bsync`、`hReport` |
| D. 本地战斗 + 事后上报结算 | **待验证** | 需要真机确认战斗是本地模拟还是服务端权威（见 04 篇路线 A） |

关键判据：**客户端没有钱包**。全包只有 1 处 `persistentDataPath` + 7 个 `PlayerPrefs` 符号，
`libkeva.so` 是火山引擎埋点 KV，不是存档。所以 A 不成立——本地拿不出"可被自己改的余额"。

另一个旁证：`res/values/strings.xml` 里只有 SDK 文案（实名、防沉迷、登录），
其中 `lilith_sdk_abuse_prevention_notice_children_timeout` = 「您今日在线时长已达上限」。
**在线时长由平台侧统计**，说明"在线/离线"这个状态本来就由服务端维护，不是客户端自报。

## 2. 离线期间，客户端会上报什么？

三层，别混在一起：

| 层 | 内容 | 断网时的行为 | 上线后会补传吗 |
| --- | --- | --- | --- |
| 会话层 | KCP 心跳、`session` 序号 | 心跳超时 → 服务端标记离线（服务端记 last_online） | 不补传，只做 `reconnect` 重建会话 |
| 埋点层 | `LilithReport` / `AliTrack` / `CrashSight` / `Keva` | 写本地磁盘队列 | **会**：恢复网络后批量补传（进数仓，不参与玩法） |
| 玩法层 | 结算/领奖/背包变更 | 断线期间的本地结算无法提交 | 只能走 `resume` → 服务端比对序号与时间戳 |

也就是说：**"离线的账号状态"是服务端自己记的，客户端不需要上报"我离线了多久"**。
真正要上报的是"离线期间产生的玩法结果"，而这在服务端权威设计里通常根本不允许产生
（断线即视为本次战斗作废，或下次登录时整局重算）。

## 3. 上线后怎么算离线状态：三种机制

| 机制 | 谁算 | 需要客户端上报什么 | 能否本地伪造 | 行业占比 |
| --- | --- | --- | --- | --- |
| 1. 服务端补算 | 服务端用自己记的 `last_logout` 与当前服务器时间差 | 什么都不用 | **不能**（改手机时间无效） | 放置类主流做法 |
| 2. 客户端上报离线时长 | 客户端算 `now - last_login` 发给服务端 | `offline_seconds` / `client_ts` | **能**（改时间/改包即可，但服务端一般有上限钳制 + 与自身记录交叉校验） | 中小厂常见 |
| 3. 离线战报队列 | 服务端逐条校验后结算 | 战斗种子、战报序列、耗时 | 取决于校验强度 | 有离线战斗的玩法 |

`Bsync`（同步）与 `hReport`（上报）两个模块名同时存在，说明**至少机制 1 和 3 的通道都在**：
`Bsync` 负责登录/重连后的状态对齐，`hReport` 负责结算类上报。

## 4. 决定性实验（30 分钟出结论）

目的：判定离线收益走机制 1 还是 2/3。**这一步不需要解密任何东西，只需要观察。**

1. 账号 A 正常在线 5 分钟，记下金币与离线收益面板数值，然后**杀进程**（不是退出登录）。
2. 用 `scripts/frida/05_hook_time.js` 把时钟偏移设为 `+6h`（`setOffset(6*3600)`），
   断网状态下等 2 分钟，恢复网络，登录，看离线收益。
3. 对照组：同一账号，`setOffset(0)`，同样断网 2 分钟后登录，看离线收益。
4. 抓包（`scripts/frida/06_net_watch.js` 或 mitmproxy）对比两次登录/`resume` 报文：
   有没有长度变化、有没有 `offline`/`seconds`/`ts` 这类字段出现差异。

判读：

- 两次收益**一样** → 机制 1，服务端权威，改本地时间/改包都无效，这条路彻底死。
- `+6h` 那次收益**明显更高** → 机制 2/3，客户端时间参与计算；接下来测**上限钳制**
  （`+240h` 看是否有 cap）与**交叉校验**（服务端拿自身 `last_logout` 对比，若差值过大是否拒绝）。
- 报文里出现明显的长度/字段差异 → 把该字段名记下来，就是后续所有"时间类"玩法的关键参数。

## 5. 方向优先级（我的建议）

| 优先级 | 方向 | 为什么 | 成本 |
| --- | --- | --- | --- |
| ★★★ | **GM 命令服务端鉴权**（`eGmSess` / `ServerContro` / `Qdebug`） | 唯一"真能改数据"的假设；日志/调试模块在包里说明代码存在 | 低（一个无害命令即可证伪） |
| ★★☆ | **离线收益时间口径**（本篇 §4） | 决定所有"时间类"玩法能否本地放大 | 低（30 分钟） |
| ★★☆ | **结算上报校验强度**（`hReport`） | 决定本地战斗数值改动是"半真"还是"全假" | 中（要改内存打一局） |
| ★☆☆ | **领奖接口幂等/重放** | 服务端实现漏洞比客户端改包更常见 | 低（重放一次） |
| ★☆☆ | 资源块替换（03 篇） | 只能改"已有值"，无法造值 | 中（要过完整性校验） |

## 6. 边界

- 实验全部在自有设备 + 测试账号上做；断网实验不要用带真实支付的账号。
- `06_net_watch.js` 只能看到密文流量（KCP/TLS），它的价值是**看长度与节奏**，不是看明文。
  要看明文必须解 parkcrypto 签名后的 HTTP 接口（见 05 篇 §4–5）。
- 不提供伪造签名、伪造离线时长、绕过服务端校验的成品脚本；本篇给的是**判定方法**。
