# 11 P0 判定：GM 面板能不能本地打开

> P0 问题：GM 命令表里的命令，是客户端自己就能开的，还是要服务端授权？
> 证据来源：真机进程内存 dump（`docs/10` 的产物），不是推测。

## 1. 结论

**客户端有完整实现，但鉴权在服务端。本地能做的上限是"把入口显示出来"，发出命令会被服务端拒绝。**

三条独立证据：

| 证据 | 内容 | 说明 |
| --- | --- | --- |
| 协议错误码枚举 | `SessionTimeout`、`SignCheckFailed`、`LoginFailed`、`EnvNotFound`、`SDKLoginFail`、`CastFailed`、`SessionClosed`、**`GMIsNotAllowed`**、`UcttWriteFailed` | `GMIsNotAllowed` 与一串**会话/签名/登录**错误并列，是**服务端返回**的错误码，不是客户端本地分支 |
| 桥接 opcode 表 | `GET_GM_COMMAND_PARAM` 出现在 `SEND_CLIENT_LOG`、`GET_FACEBOOK_TOKEN`、`WX_UPLOAD_FILE`、`GET_CASHIER_CONFIG`、`REPORT_SLS` 同一张表里 | GM 命令走的是**和登录/支付同一套桥接协议**，参数从服务端来，不是本地拼的 |
| 面板规模 | 31 个 Tab 模块 + `GMCommands` / `GMCommandGroup` / `GMMainPanel` / `GMEntranceController` / `GMButtonEnable` | 有 UI，有控制器，说明"显示/隐藏"确实是客户端逻辑 —— 但**显示 ≠ 生效** |

## 3. 客户端侧确实有开关（但只控显示）

- `GMButtonEnable`、`GMEntranceController` —— 入口按钮的启用/禁用
- `isDebugMode`、`get_debugMode`、`enable_debug`、`DEBUG_MODE`、`isDebugBuild`
- 本地存档键：`GM_MainViewOpenList_Enabled`、`GM_CommercialPopup_LastRealPayDays`
- 日志串：`[MainViewInterludeOpenList] StartMainViewOpen skipped (GM/local storage disabled…`
  → 客户端确实有"GM 开关 或 本地存储"的短路逻辑

这些都能被本地改（改 Lua 常量、改 `PlayerPrefs`/kv、改内存），**但改完只是让面板出现**。
面板里点下去会走 `GET_GM_COMMAND_PARAM`，服务端按账号的 GM 权限判定，不在白名单就回 `GMIsNotAllowed`。

## 4. 所以 P0 的答案对整体路线意味着什么

| 原假设 | 现状 |
| --- | --- |
| "GM 面板是本地开关，打开就能刷" | **否**。开关只控显示；命令要过服务端权限 |
| "GM 是 C 层（资产层）突破口" | 关闭这条。除非能拿到一个**已被授权的 GM 账号**，否则客户端侧无解 |
| "GM 面板没有客户端实现" | 否，有 31 个 Tab 的完整实现 —— 这反而说明它是**给内部/QA 用的正规功能**，权限自然在服务端 |

**C 层（金币/通行证真实数值）到此可以定性：客户端改不出来。** `docs/04` 的矩阵维持不变，
只是现在有了"为什么改不出来"的确切机制（服务端错误码 + 桥接 opcode 存在）。

## 5. 剩下还有价值的方向

P0 关掉了一条路，但也顺带照亮了别的：

1. **`hReport` / `Bsync` 的战报字段**（P2）—— 本地战斗结算上报了什么，服务端拿什么复算。
   这是唯一还可能"用客户端影响资产"的地方（比如上报的伤害/回合数有没有上限校验）。
2. **通行证表结构**（P1）—— `Config/PassLevel` / `PassParam` 是客户端算还是服务端下发，
   决定"本地显示错了会不会被纠正"。价值低于 P2，但成本也低。
3. **`Config/GMCommands.luae` 的命令名清单** —— 即使不能用，也能反推服务端有哪些内测用命令，
   是理解经济系统设计（比如有没有"直接发金币"的 GM 命令）的旁证。
