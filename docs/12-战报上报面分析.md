# 12 P2：战报/结算上报面分析

> P2 问题：本地战斗打完，客户端到底上报了什么？服务端拿什么判断"这场是真的"？
> 证据来源：真机内存 dump（`docs/10` 同源），扫描脚本 `scripts/13_scan_report_surface.py`。

## 1. 结论

**结算不是"客户端报个数字"，而是"客户端交一份可复算的战斗记录"。**

服务端有 `BattleSimulator` + 确定性随机 `Src.Tools.BattleRandom` + `GetRoundData`/`GetRoundOperations`
这套模型，配合 `battleCheckVersion` 选择校验规则，能把客户端交上来的记录重跑一遍再比对结果。

所以「把 `killZombieCount` 改成 999」这种改法，记录与结论对不上，一定被拒。
真正的关键问题从"改数字"变成了"**改输入**" —— 详见 §4。

## 2. 协议字段（全部为内存里的标识符原文）

### 2.1 请求与打包

| 标识符 | 含义 |
| --- | --- |
| `ReqStartBattle` / `ReqEndBattle` | 战斗开始/结束（`battleId` 由服务端下发） |
| `ReqBattleSettle` / `ReqAreaBattleSettle` | 结算提交（含区域战斗） |
| `PackBattleReqField` | **唯一的战斗字段打包函数**（全包只有这一个 `Pack*Field`） |
| `PackBattleSlotID` | 槽位 ID 打包 |
| `PackChallengeFieldsFromFormation` | 从阵容打包挑战字段 |
| `ReqReportClientRawResult` / `ReportClientRawResult` | "客户端原始结果"上报（另一条通道，疑似埋点/审计） |
| `ReportBattleLog` / `TryReportBattleLog` / `reportClientData` | 战报日志上报 |

### 2.2 客户端声明的字段

```
damage              rounds              killZombieCount     leftZombieCount
clientBtVersion     battleCheckVersion  hasBtRecord         formationTeams
bossGroup           btUids              ownerLastUID        boughtCount
buyCountLimit       maxDamagePct        _maxDamage          _maxDamagePercent
_periodMaxDamage    _battleID           _curFloor           ownTs
```

### 2.3 记录本体（关键）

```
BtInput  BtInputExt  BtInputR  BtInputRound  BtRecord  BtRecordEntry
BtRecordPetEntry  BtRecordRec  CacheBtRecord  Dn_RecBtRecord  msg.BtInputExt
GetBtInputRound  GetRoundData  GetRoundOperations
GetSelfStats  GetOppoStats  GetUnitMaxHp  GetTotalDamageByUID  GetFormationTeam
```

`BtInputRound` + `GetRoundOperations` 说明记录是**逐回合、逐操作**的：每一回合里谁放了什么技能、
打中谁、伤害多少。`BtRecordPetEntry` 说明宠物/召唤物单独建条目。`clientBtVersion` 是这套记录的格式版本。

## 3. 服务端复算链（推断，有字段支撑）

```
客户端                      服务端
ReqStartBattle  ─────────▶ 分配 battleId / 种子 / battleCheckVersion
  本地打完（BT + BattleRandom 决定性随机）
ReqEndBattle    ─────────▶ BattleSimulator 按 BtInput* 重放
 { BtInput*, damage,            ↓ 比对 damage / rounds / killZombieCount
   rounds, killZombieCount,     ↓ 不合就拒（GMIsNotAllowed 是另一类，这里是普通校验失败）
   clientBtVersion,          BattleSampleLogs 抽样落审计
   battleCheckVersion,       maxDamagePct / _periodMaxDamage 排行榜侧二次限制
   hasBtRecord }
```

`BattleSampleLogs` 是一条独立的抽样审计路径 —— 说明不是每场都全量复算，
而是**抽样复算 + 阈值筛查**。这对第 4 节的可验证缺口很重要。

## 4. 三个可验证的缺口（按性价比排序）

### 4.1 `hasBtRecord` 降级路径（最值得验）

字段存在即说明"有没有记录"这件事是可协商的。合法的 `false` 场景一定有
（老客户端、热更失败、低端机超时）。

**若 `hasBtRecord=false` 时服务端退化成弱校验，那么伪造结果数字就够了。**
这条不需要改客户端逻辑，只需要观察：正常打一场，抓 `ReqEndBattle`，看 `hasBtRecord` 是 `true` 还是 `false`、
记录字段占多少字节。**这是 P2 里唯一有可能一步到位的地方。**

### 4.2 `battleCheckVersion` 自报版本

版本号由客户端上报。如果服务端按"客户端报的版本"选规则，那么旧版本规则可能更宽
（典型现象：老版本客户端能过、新版本不能过）。验证方法同样是抓包看这个值是否被服务端接受/覆盖。

### 4.3 「改输入」这条路：复算防不住自洽的伪造

这是本次分析最重要的判断：

> 如果服务的复算用的是**同一套 BT + 同一个 `BattleRandom`**，那么"让本地随机数偏向好结果"
> 所产生的记录，在服务端重放时**也会得到同样（超模）的结果** —— 记录是自洽的。

也就是说 record-replay 防的是「**改结论**」，防不住「**改输入的产生过程**」。
真正的闸门在于服务端对**输入合法性**的约束，而不是对结果的比对：

| 闸门 | 证据 |
| --- | --- |
| 回合数/操作数上限 | `rounds` 字段 + `buyCountLimit` 类上限模式 |
| 伤害占比上限 | `maxDamagePct`、`_maxDamagePercent`、`_periodMaxDamage`（排行榜/世界 Boss 侧） |
| 操作频率/冷却 | 需动态确认（`GetRoundOperations` 里若有时间戳则可查） |

所以本地的现实上限是：**让战斗打得更好看**，但只要服务端有"每回合最多几个操作 / 伤害不超过最大血量百分比"这类约束，
就不会变成资产。结合 P0（GM 入口锁死），**金币/通行证仍然改不出来**。

## 5. 与 P0 合并后的整体判断

| 层 | 结论 | 依据 |
| --- | --- | --- |
| GM 入口 | 服务端权限（`GMIsNotAllowed`） | `docs/11` |
| 结算上报 | 服务端复算（`BattleSimulator` + `BtInput*` + `battleCheckVersion`） | 本文 §2、§3 |
| 排行榜/世界 Boss | 百分比上限二次限流（`maxDamagePct`） | 本文 §2.2 |
| 客户端能做的 | 改显示、改输入质量、试 `hasBtRecord` 降级 | 本文 §4 |

## 6. 下一步实验（真机，只读/抓包级）

1. 抓 `ReqStartBattle` → `ReqEndBattle` 一对报文，量出 `hasBtRecord`、`BtInput*` 的实际长度与取值。
2. 同一关卡打两次（一次胜利一次失败），比较 `battleCheckVersion` 是否变化 → 判断版本是"客户端自报"还是"服务端下发"。
3. 断网重连后再结算，看是否补传 `BtRecord` → 判断记录是否可缓存后统一上报。
4. 只在**自有账号**上做，不改内存、不重放请求、不伪造报文。
