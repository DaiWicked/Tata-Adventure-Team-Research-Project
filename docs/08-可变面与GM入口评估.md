# 08 · 可变面与 GM 入口评估

> 回答四个问题：**能改什么 / 开发者命令是否有效 / 有没有 UI 入口 / 本地战斗数值能不能改**，外加"真机研究还能挖到什么"。
> 全部结论都挂在本仓库已有的静态证据上（`docs/02`–`docs/07`、`notes/08-pkg-strings.txt`），没有抓包的项一律标注"待动态验证"。

---

## 0. 一句话

- **能改的**：屏幕上的数字、资源文件、内存里的显示值。**改不动的**：服务端账本里的金币和通行证。
- **GM 命令**：客户端只负责"发请求"，判定在服务端；包里有 `GmSess` / `Debug/GMBase` / `Tabs/GM` 这些**入口定义**，但没有权限就无法生效。
- **UI 入口**：**有**。包里存在 `Tabs/GM`（GM 面板的页签定义）与 `Debug/GMBase…`（调试基类脚本）。默认不可见，是否可见由服务端/开关决定。
- **本地战斗数值**：能改"看到的"和"这一局上报的结果"，能不能算数取决于服务端是否复算（`hReport` 结算上报），静态只能确认"有上报层"，**不能**确认"服务端采信"。
- **真机还能查到更多**：会，而且量级远大于静态——解密后的元数据（全部类名）、解密后的 Lua（真正的公式与 GM 处理函数）、抓包（结算是否被复算、离线收益谁算）。

---

## 1. 能改什么：按"改完之后算不算数"分三档

| 档 | 对象 | 手段 | 生效范围 | 证据 |
|---|---|---|---|---|
| **A 只能改自己屏幕** | 金币显示数、等级、战力、背包图标、皮肤、文本、UI 数值 | 内存改（Frida `Interceptor` 改 getter）、Lua 运行时改常量 | 只在本机渲染；任何一次服务端下发（登录、进战斗、切场景、重连）都会被覆盖 | `docs/04` 1.1「客户端无钱包」：全部数值来自服务端协议包 |
| **B 改一次，能撑到下次校验** | 本地战斗的中间态（血量、伤害、CD）、商店里已下发到本地的价格/库存缓存、离线收益的时长参数 | 同上 + 改系统时钟 | 依赖下一次校验点；若结算由服务端复算，结束即失效 | `docs/06` §3 三种离线收益机制表 |
| **C 真的影响账号资产** | 金币余额、通行证等级、领奖、充值到账 | **必须有服务端参与**（复算漏洞 / 越权 / 幂等重放 / 签名伪造） | 只有这一档才算"作弊成功" | `docs/02` 六层防护、`docs/04` 矩阵 |

→ 静态能给出的硬结论：**A 档随便改，B 档看校验点，C 档客户端改不出来**。`InpackageFileHash.Android.jsonbin` 的文件哈希清单还额外堵死了"改包"这条路（`docs/02`）。

## 2. 开发者命令是否有效

先分清包里的三类"开发者东西"：

| 证据 | 位置 | 是什么 | 能否本地生效 |
|---|---|---|---|
| `GmSess` | `notes/08-pkg-strings.txt` 0x008824 kind5 | GM **会话对象**（一次 GM 操作的服务端会话） | 否——会话由服务端开 |
| `Debug/GMBase…` | 同上 0x008804 kind5 | GM **基类脚本**（按键/指令注册） | 否——只负责组装请求 |
| `Tabs/GM` | 同上 0x008839 kind5 | GM **UI 页签**（面板入口定义） | 否——可见性由开关/权限决定 |
| `GMSearch` | 0x00F1BC kind9 | GM 搜索（通常是查玩家/查物品） | 否 |
| `MCommand` | 0x00F17C kind6 | 指令分发（manager command） | 否 |
| `ProtoTestForg` | 0x005039 kind2 | 协议测试/构造（Proto Test Forge） | 否——测试工具，线上包不应可达 |
| `LocalBug` / `TestStage` | 0x0050A0 / 0x01962C | 本地 bug 上报 / 测试关卡 | 前者只上报，后者需服务端放行 |

结论：**GM 命令的有效性 100% 在服务端**。客户端这一侧只存在"把指令打包成协议 + 签名（`parkcrypto_generate_signature`）"的能力，即使你在本地把 `Tabs/GM` 强制显示出来、把 `GmSess` 造出来，发出去的包仍要过服务端的角色权限校验。

值得动态盯的只有一处：**服务端是否只校验"这个账号是不是 GM"，还是连指令参数也校验**。如果是前者，问题就退化成"怎么拿到一个 GM 账号"；如果是后者（存在参数层面的注入/越权），那才是真漏洞。这条已列在 `docs/04` 1.4 与 `docs/05` §6 验证清单里，标记 ★★★。

## 3. 有没有 UI 交互界面和入口

**有，但要区分三种"入口"**：

### 3.1 游戏内 GM 面板（`Tabs/GM`）
- 证据：`notes/08-pkg-strings.txt` 里 0x008839 存在条目 `Tabs/GM`（tag=0x75 → L=7, kind=5），同区还有 `GmSess`（0x008824）、`Debug/GMBase`（0x008804）。
- 判读：这是个**页签路径**，说明客户端里有一份 GM 面板的 UI 定义（未被删掉的调试残留，或者留给客服/测试用）。
- 现状：默认不可达。常见做法是 `if (gmEnabled)` 才注册该 tab，`gmEnabled` 来自服务端下发或本地开关（`PlayerPrefs`/`keva`）。静态看不到 `gmEnabled` 的来源，因为那段逻辑在加密 Lua 里。
- 想验证它：真机上 hook Lua 的 tab 注册函数，或直接把 `Tabs/GM` 的判定改成 true（本地可见 ≠ 能用，见 §2）。

### 3.2 系统层入口（85 个 activity，7 个 exported）
`apktool_out/AndroidManifest.xml` 里可被外部拉起的组件（都不是 GM，是三方 SDK 回跳）：

| 组件 | exported | 用途 |
|---|---|---|
| `com.farlightgames.igame.SplashActivity` | true | 主入口（Unity 容器） |
| `com.lilith.sdk.base.activity.ParkAuthActivity` | true | 平台登录（scheme `com.lilithgame.pgame.android.cn`） |
| `com.tencent.tauth.AuthActivity` | true | QQ 登录回跳 |
| `...wxapi.WXEntryActivity` / `WXPayEntryActivity` | true | 微信登录/支付回跳 |
| `com.alipay.sdk.app.AlipayResultActivity` | true | 支付宝结果回跳 |
| `androidx.core.content.FileProvider` | **false** | 文件共享（已关闭外部访问，好事） |

- 深链：`pgame-obt.go.link`（AppsFlyer OneLink）、`https://link-pgame.lilithgame.com/...`、`parksdk://`。这些是**归因与登录回跳**，不是调试入口，但它们是唯一能从外部触发 App 内部逻辑的路径——如果要找"外部拉起 → 参数注入"的洞，只看这几条。
- 全部 85 个 activity 里**没有** `GM`/`Debug`/`Console`/`Test` 命名的组件；`android:debuggable="false"`、`sdkDebug=NonDebuggable`。

### 3.3 WebView 页面（最容易被忽略的一类）
- `assets/park/index.html`、`assets/forum/index.html`：平台/论坛的内嵌页（走 `park_server_region: lilith`）。
- `assets/lilith_sdk_modules/` 下 15 个 **0 字节** 占位模块（`PspModuleLoader`、`PaymentModuleLoader`、`ReportModuleLoader`…）——真正的实现由平台热下发。
- `res/values/strings.xml` 存在一组混合容器风格的调试串：
  `debug_mode_remind_message` = 「现在是 Debug 模式，仅能用于测试，必须关闭该模式后才能提审…关闭 debug 模式：debug_mode 配置为 false 且移除 devtools 依赖」
  → 说明包内嵌了**带 devtools 的混合渲染容器**（Weex/uni-app 一类）。这类容器历史上有"调起 devtools / 远程调试端口"的经典问题，但要看 `debug_mode` 的实际取值与是否 release 剥离——静态只能确认字符串在，**不能确认开关状态**。

> 结论：**有 UI 入口，也有调试残留**，但它们都不是"输个命令就加金币"的东西。`Tabs/GM` 是最值得动态验证的一个点。

## 4. 本地战斗数值能不能改

分三层看，每层的答案不同：

| 层 | 能否改 | 依据 | 改了会怎样 |
|---|---|---|---|
| **表现层**（伤害飘字、血条、CD、暴击特效） | 能，随便改 | 这些是本地渲染，`BattleFx`/`CastPlay`/`SkillCamera`/`ChainEffect` 全在包内（`docs/07` §5） | 只有自己看到 |
| **战斗过程**（本地跑的行为树 + Lua 判定） | 能改（内存或 Lua 运行时） | 名字表里 `Parallel`/`Reaction`/`ECF/System`/`Evaluate` 是行为树/判定节点；战斗确实在本地跑（否则不需要这些） | 这一局的中间结果会被本地逻辑接受 |
| **战斗结果入库**（经验、掉落、通行证任务进度） | **看服务端** | 存在 `hReport`（结算上报）与 `Bsync`（状态同步）；`docs/06` §2 三层上报表 | 服务端复算 → 作废；服务端采信 → 可行（这才是真漏洞） |

所以"本地战斗数值能不能改"这个问题，**准确答案是：能改，但只有"服务端不校验的那部分"才有意义**。判断"校验不校验"唯一的办法是抓一次结算包：改前改后各打一局，看服务端下发的经验/掉落是否跟着变。

配套实验（已在 `docs/06` §4 写过，这里收敛成三条）：
1. 同一关卡，正常打 → 记录结算包响应（基准）；
2. 改本地伤害（Frida 改技能倍率）→ 打同一关 → 对比结算响应是否一致；
3. 改系统时钟 +6h → 看离线收益是否真的变多（判"离线收益谁算"）。

## 5. 真机研究会不会查到更多漏洞

**会，而且是质变级的**。静态已经把"能看到的"看到底了；下面这些只有真机能拿到：

| 真机动作 | 新获得的能力 | 可能直接产出的漏洞 |
|---|---|---|
| dump 解密后的 `global-metadata.dat`（`docs/05` §2） | **全部业务类名/方法名**（现在只能看到被截断的资源名） | 找到真正的 GM 判定函数、结算校验入口、`gmEnabled` 的来源 |
| dump 解密后的 Lua（`docs/05` §3） | 战斗公式、经济系统实现、GM 指令处理函数、`parkcrypto` 的签名字符串拼法 | GM 参数注入、领奖幂等、客户端可伪造字段清单 |
| hook `parkcrypto_generate_signature`（`docs/05` §4） | 签名入参的完整结构（含 `os_type`） | 重放/伪造请求的前置条件是否只差一个签名 |
| mitmproxy 抓包（`docs/05` §5） | 结算包、离线收益包、通行证下发包的真实字段 | 结算是否复算、离线时长是否客户端上报、通行证进度是否增量下发 |
| 完整性校验实测（`docs/05` §6） | `InpackageFileHash` 到底在校验什么、什么时候校验 | 改包是否真的会被拦（现在只是"存在清单"，没有实测） |

**优先级**（按"投入产出比"排）：
1. 抓包看结算与通行证下发 —— 不需要脱壳，半小时能有结论；
2. dump Lua —— 一次性拿到全部经济逻辑，代价是要过反调试；
3. 元数据 dump —— 拿到类名后才能精确定位函数，属于"做深"的前置；
4. 签名 hook —— 只有在"要伪造请求"时才需要，风险最高、收益取决于 1 的结果。

## 6. 边界

本文件全部基于包内静态证据；标"待动态验证"的四项（结算是否复算、离线收益谁算、`Tabs/GM` 的开关来源、完整性校验时机）在没有抓包前都只是假设。动态部分需要在自有设备 + 测试账号上进行，且不改动任何线上数据。
