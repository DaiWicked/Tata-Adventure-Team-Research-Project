# 02 保护栈与对抗面

这个包的防护是「四层叠加」，每层都留了可验证的痕迹。按「从外到内」排列：

```
① APK 签名 / 二次打包检测
② dex 加密（易盾壳）           → classes.dex 只有 30 个壳 stub
③ IL2CPP 元数据加密（HTPX）    → 业务类名/方法名全不可读
④ 资源加密 + 完整性哈希清单    → .luae/.jsone/.pkg/lpak 全部加密，且有 hash 清单
⑤ 请求签名（libparkcrypto）    → 所有 API 参数签名，os_type 参与
⑥ 反调试 / 反注入 / 反模拟器   → libcheck + libNetHTProtect
```

## ① APK 签名

- `META-INF/PGAME_CN.RSA` + `META-INF/PGAME_CN.SF`（v1），并带 v2 签名块
  （`APK Sig Block 42` 位于 offset 357,515,524）。
- `libsigner.so` 里是 **Adjust SDK** 的签名辅助
  （`Java_com_adjust_sdk_sig_NativeLibHelper_nSign`），不是 APK 校验器；
  APK 自身的签名校验由易盾 `libNetHTProtect`/`libnesec` 承担。
- 佐证：`assets/probeSoMd5Record.txt` 里逐 ABI 记录了三套编译器的 so 指纹
  （`llvm-a20`/`gcc-a16`/`gcc-b16`），这类「预期指纹表」就是给运行时自校验用的。
- 实操含义：**重打包必然破坏签名**，要么改签名校验点（在壳里，成本高），
  要么走动态（Frida 注入，不改文件）。

## ② dex 加密（网易易盾）

`classes.dex` 反编译后只有 **30 个 Java 文件**，全部落在两个包：

```
com/netease/nis/wrapper/*        ← 壳入口（MyApplication、MyJni、stub Application/Activity）
a/auu/a.java                     ← 工具类（含字符串解密函数）
```

真实 dex 在运行时由壳从 `assets/libnesec.so`（加密形态）解开并内存加载。壳的加载流程
（`MyJni.java` 反编译结果 + 字符串还原）：

1. 从 `assets` 取 `libnesec.so`，写到 `context.getFilesDir() + "/templib"`；
2. 前 4 字节 `^ 0x37` 后写到 `<dir>/libnesec.so`，再 `System.load()`；
3. 判断 `Build.CPU_ABI` 是否含 `x86` / `x86_64`（模拟器倾向）；
4. 读 `Settings.Secure["adb_enabled"]`，`>0` 视为已开 ADB —— 这是**反调试的第一道判断**；
5. manifest 里埋了 `meta-data android:name="BUGRPT_SWITCH" android:value="on"`，用于控制壳的行为分支。

### 字符串混淆已还原

`a/auu/a.java` 的 `c(String)`：先 base64 解码，再逐字节 XOR `"NetEase"`（`{78,101,116,101,97,115,101}`）。
用 `scripts/05_decode_yidun_strings.py` 还原出的关键项：

| 密文 | 明文 | 含义 |
| --- | --- | --- |
| `IgwWCwQAAC0=` | `libnesec` | 解密库名 |
| `IgwWCwQAAC1LBwo=` | `libnesec.so` | 落地文件名 |
| `YQkdBw8WFisGWhYO` | `/libnesec.so` | load 路径 |
| `YRERCBEfDCw=` | `/templib` | 中间落盘目录 |
| `LwEWOgQdBCwJEQE=` | `adb_enabled` | Settings.Secure 键 |
| `DDAzNzEnOh0yPTEiOw==` | `BUGRPT_SWITCH` | manifest meta-data 键 |
| `Nl1C` / `Nl1COldH` | `x86` / `x86_64` | 模拟器判断 |

→ 结论：壳层已经没有秘密，**剩下的难度全在 native 解密与运行时校验**。

## ③ IL2CPP 元数据加密

`assets/bin/Data/Managed/Metadata/global-metadata.dat`（10,033,692 B）的头部是：

```
48 54 50 58  ("HTPX")  1c 1a 99 00  e9 7f 51 a1 7d 36 f4 a9 ...
```

- 原生 IL2CPP 元数据 magic 应为 `0xFAB11BAF`；这里被换成了易盾容器 `HTPX`。
- 直接后果：`libil2cpp.so` 里 61 MB 只能看到引擎自身符号（`il2cpp_*`、`tolua_*`、
  `Cinemachine.dll`/`LitJson.dll`/`Assembly-CSharp.dll` 这类程序集名），
  **任何业务类名都搜不到**（`Gacha`/`Hero`/`BattlePass`/`Recharge` 全部 0 命中）。
- 这一点很关键：**静态 il2cpp dump 路线被堵死**，除非先在运行时 dump 出明文元数据。

## ④ 资源加密 + 完整性哈希

- 加密容器：`FF FF FF FF | u32 长度 | 密文`，覆盖 `AppInfo/Config/Game/Localization.jsone`、
  `Config/LanguageDbZH.luae`、`pgame.pkg`；`nedata.db` 是另一种（无此头）。
- 完整性：`assets/InpackageFileHash.Android.jsonbin`(163,636 B) 是 `JSON` 开头的自定义
  二进制清单，内含 `AppInfo.json`、`pgame.pkg`、`aa/Android/*.bundle`、`*.lpak` 等
  152 条候选路径 + 哈希。另有 `InpackageAACatalog.bin`(233,080 B)。
- `assets/aa/Android/inpackage_aa_1.lpak`(236 MB) 与 `catalog.bundle` 走 **Unity 官方
  AssetBundle 加密**（UnityPy 判定：`The BundleFile is encrypted, but no key was provided`，
  并给出 `key_sig=46057f107ae966a5`、`data_sig=9b67bff01fcf00c9`）。
  用 UnityPy 的 `brute_force_key` 在 `global-metadata.dat`、`libil2cpp.so`、`libigame.so`、
  `libunity.so`、`libnesec.so` 里都**没找到密钥** → key 是运行时拼出来的。

含义：改一个 `.luae` / `.lpak` 文件，不但要过加密，还要过 hash 清单。**改包的成本远高于改内存。**

## ⑤ 请求签名（libparkcrypto）

`libparkcrypto.so`(23,304 B) 导出：

```
parkcrypto_build_signature_base_string
parkcrypto_rfc3986_encode / parkcrypto_url_encode
parkcrypto_generate_signature
parkcrypto_json_parse / parkcrypto_json_get
parkcrypto_get_version
```

日志串（说明它自己的行为）：

- `get_decrypted_secret: unknown os_type=%s, using default win prod key`
- `parkcrypto_generate_signature: missing required parameter: os_type`
- `input=%s`

→ 典型「参数排序 + RFC3986 编码 + secret 拼接 + 摘要」的签名方案，`os_type` 是参与签名的字段之一，
secret 是**解密得到**的（不是硬编码字符串）。这决定了：**抓包改包必须 hook 签名函数，
或者让签名函数替你签**（见 05 篇）。

## ⑥ 反调试 / 反注入 / 反模拟器

`libcheck.so`(46,032 B) 的字符串（原文）：

```
Java_com_lilith_sdk_check_lib_common_NDKUtil_CK
/system/bin/libtthook.so
/system/lib/libc_malloc_debug_qemu.so
/mnt/sdcard/buildroid-gapps-ics-20120317-signed.tgz
Emulator
%s %s  exsits, emulator!
```

→ 检测注入库（`libtthook.so`）、QEMU 调试库、典型模拟器目录，命中即上报。

`libNetHTProtect.so`(5.76 MB) 是易盾 App 保护主体，自带 TLS 栈
（字符串含 `-----BEGIN CERTIFICATE-----`、`TLSv1.3`、`TLS-RSA-WITH-AES-256-CBC-SHA256`），
自带 HTTPS 通道 + 完整性上报。

## 攻击面小结（按性价比排序）

| 对抗点 | 静态可绕过？ | 动态可绕过？ | 备注 |
| --- | --- | --- | --- |
| dex 加密 | 否 | 是（内存 dump） | 但业务逻辑不在 dex 里，收益低 |
| 元数据加密 | 否 | 是（dump `global-metadata.dat` 明文） | 做完才能谈「看懂逻辑」 |
| 资源加密 | 否（密钥运行时拼） | 是（hook 解密函数直接拿明文） | **Lua 逻辑、数值表都在这里** |
| 完整性 hash 清单 | 否 | 是（patch 校验点或 hook 比较函数） | 只拦「改文件」，不拦「改内存」 |
| 请求签名 | 否 | 是（hook `parkcrypto_generate_signature`） | **改包/重放的必要条件** |
| 反调试/反注入 | 部分（字符串可 patch） | 需要 Magisk DenyList + 隐藏 Frida | 见 05 篇前置条件 |
