# 03 资源容器与块加密：一个可利用的结构

这一篇是本项目最「可操作」的发现：`.jsone` / `.luae` / `pgame.pkg` 使用的不是安全流密码，
而是**8 字节分组的确定性块加密（ECB 语义）**，密钥全局共用。这让「不解密也能篡改明文」
成为可能。

## 1. 容器格式（实测）

```
偏移 0x00  FF FF FF FF           magic
偏移 0x04  u32 little-endian      明文字节数（不是密文长度！）
偏移 0x08  ciphertext             长度 = 明文长度按 8 字节向上取整
```

实测对照（`scripts/03_probe_asset_container.py`）：

| 文件 | 文件大小 | 声明长度 | 密文长度 | 补齐 |
| --- | --- | --- | --- | --- |
| `AppInfo.jsone` | 336 | 324 | 328 | 324→328（+4） |
| `Config.jsone` | 632 | 617 | 624 | 617→624（+7） |
| `Game.jsone` | 1536 | 1526 | 1528 | 1526→1528（+2） |
| `Localization.jsone` | 688 | 676 | 680 | 676→680（+4） |
| `Config/LanguageDbZH.luae` | 423,304 | 423,296 | 423,296 | 已对齐（+0） |

**所有补齐都恰好对齐到 8 字节**——这本身就是「分组长度 = 8」的独立证据。

`pgame.pkg`(19,472,168 B) 头不同：`FF FF FF FF | d4 d8 02 00`，`0x2D8D4 = 186,580`，
不是明文长度而是分块参数；但其密文呈现同样的 8 字节块特性（见下）。

## 2. 判定依据：8 字节块重复统计

如果加密是「位置相关」的（CTR/CBC/流密码），同样的明文在不同位置必然产生**不同**密文；
如果是 ECB（8 字节分组、全局密钥），同样的明文块会产生**完全相同**的密文块。

对整份文件按 8 字节切块统计重复（`scripts/03_probe_asset_container.py` + 内联统计）：

| 文件 | 8B 块总数 | 重复组数 | 落在重复组的块数 | 随机碰撞期望 |
| --- | --- | --- | --- | --- |
| `pgame.pkg` | 2,434,020 | **123,134** | **723,922（29.7%）** | 1.6e-07 |
| `LanguageDbZH.luae` | 52,912 | 104 | 286 | 7.6e-11 |
| `nedata.db` | 1,623,612 | **0** | 0 | 7.2e-08 |

- `pgame.pkg` 近 30% 的块是重复块，最高单块重复 **6,516 次**（`97eed49415102796`）——
  这个块同时也是 `LanguageDbZH.luae` 密文的**第一个块**：同一个明文块（几乎可以肯定是
  全零填充）在两个不同文件里得到同一个密文 → **密钥全局共用 + 无 IV + 确定性映射**。
- 远距离重复也在：`LanguageDbZH.luae` 中 `987b613ba3a89c5b` 出现在偏移 100,216 与 346,232
  （相距 240 KB）；共 83 组重复的距离 > 10 KB。
- 若按 16 字节切块，重复组只有 9 个（且集中在同一处高冗余区），说明**分组长度是 8 而不是 16**。

### 排除「短周期重复密钥 XOR」

对 `LanguageDbZH.luae` 做归一化 Hamming 周期检测（k=4..128，块间距离）：

```
k=9  3.722 bit/byte     k=14 3.768     k=25 3.770
k=32 3.758              k=21 3.827     k=68 3.862
```

最优也只到 3.72（随机期望 4.0），没有哪个 k 掉到接近 0 —— **不存在短周期重复密钥**。
所以它不是「循环 XOR 一个 16 字节 key」，而是真正的 8 字节分组密码。

### 排除标准算法

`scripts/04_scan_crypto_consts.py` 在全部 32 个 arm64 so 里扫特征常量：

- AES S-box `637c777bf26b6fc5`：只在 `libCtaApiLib.so`(广点通) 与 `libunity.so` 命中；
- DES IP 表、Blowfish π 表、SM4 FK、XXTEA delta `b979379e`、ChaCha20 sigma：目标库全部未命中；
- `libil2cpp.so` / `libigame.so` / `libnesec.so` 均无任何标准对称算法常量。

→ 8 字节分组 + 非标准实现 = **自定义 Feistel / TEA 变体 / 私有 S 盒**，密钥与算法参数在
运行时装配（静态找不到）。`nedata.db` 无块重复，还用了**另一种**模式（流式/CBC），
说明数值表与脚本包是两套加密。

## 3. 这个结构能干什么

ECB 的经典问题在这里全部成立，而且**不需要密钥**：

### 3.1 已知明文块表（block dictionary）

同一个明文块 → 同一个密文块。因此可以建立「密文块 → 明文语义」的字典：

- 已知明文片段（JSON 结构、`{"id":`、`"price":`、`"gold":`、UTF-8 中文串）可以先离线加密成
  密文块（前提是拿到密钥，见 05 篇 hook），之后用来**定位**配置文件里的对应字段；
- 更进一步，纯统计也能定位：例如全零块 `97eed49415102796` 反复出现的位置，就是对齐填充位，
  字段边界随之暴露。

### 3.2 块替换（cut & paste）—— 改数值的实用手法

因为分组独立 + 全局密钥，**把一个块从 A 处搬到 B 处，B 处就变成 A 处的明文**：

```
原：... [块X = "price":1] [块Y = "00"     ] ...   ← 价格 100
改：... [块X = "price":0] [块Y = "00"     ] ...   ← 价格 000，块X 取自别处
```

含义：**改出来的数值只能取「语料库里已存在的值」**（比如把某商品价格改成另一处已出现过的
`0`、`1`、`999`）。对配置表这种天然包含大量重复数值的文件，命中率很高；想改成任意值则需要
密钥（回到 05 篇）。

### 3.3 前提与限制

1. **完整性清单**：`InpackageFileHash.Android.jsonbin` 记录了 `AppInfo.json`、`pgame.pkg`、
   `aa/Android/*.bundle`、`*.lpak` 的哈希。改文件 → 哈希不匹配。要落地必须同时处理校验点
   （patch 比较函数或 hook），否则只能停留在「内存里改」。
2. **重打包签名**：改 assets 就要重签 APK，签名校验在易盾 native 层（见 02 篇）。
3. **服务端权威**：即使把本地价格表改成 0，**下单金额仍由服务端算**，这一点在 04 篇展开。
4. 我**没有**在本项目里对 `pgame.pkg` 做实际块替换（那属于篡改样本，且需要先过完整性校验）；
   本篇只给出「该结构存在且可利用」的证据与方法。

## 4. 一句话总结

> 加密是「8 字节 ECB + 全局密钥 + 非标准算法」：**抗逆向强度不低（算法不公开），但抗篡改强度很低
> （无 IV、无链接、无 MAC）**。对「让客户端显示不一样的东西」这类目标，这是最短路径；
> 对「凭空造出金币」这类目标，它一点用都没有——因为金币不在这些文件里。
